# 创意空间 · 统一发布协议

适用于七个子项目及共享设施。自 2026-10-28 起，全部在创意空间一个 Codex 项目内管理；不再要求独立子项目对话提交结果或通知总项目。

## 本地完成与发布分开

用户已确认：先完成本地修改和验证，等待用户说“推送”再发布。本地交付时说明变更、验证和未测范围；不自动提交、打标签、推送或部署。收到发布授权后，连续完成下列流程，不逐步重复确认。

## 1. 明确发布基线与范围

```bash
git status --short --branch
git worktree list
git fetch origin --tags
git rev-list --left-right --count HEAD...origin/main
```

确认本次涉及的文件。旧基线或脏工作区先比对，保留本地独有内容后再衔接最新远端；不要直接覆盖，不把已上线代码重复当成新功能。多个任务的成果按顺序集成，发布期间再次检查远端 main 有无变化。

若使用隔离工作树，结束时把已验证提交与必要的本地记录协调回统一工作入口，不让主目录长期停留在旧 HEAD。工作树不是新的独立项目。

## 2. 本地验证与记录

1. 本地只保留当前源码，历史使用 GitHub 提交/标签；修改后跑对应项目专项验证，必要时做浏览器检查。
2. 维护 `project.md`、源码 SHA-256、子项目 `更新记录.md`、根本地总记录与状态台账。仅文档变更无需归档未变的业务源码或增加业务版本。
3. 明确文件路径暂存并审阅 `git diff --cached`，不得用无差别 `git add -A` 吞并其他任务内容；根总记录不提交。
4. 对候选提交及其本地版本标签生成目录，运行全项目门禁和发布包检查：

```bash
node 创意空间首页/scripts/generate-game-catalog.cjs
node scripts/check-all.cjs
node 创意空间首页/scripts/write-deployment-meta.cjs
node scripts/build-site.cjs
node 创意空间首页/测试/site_package_test.cjs
```

本地 `TEST_PYTHON` 指向已具备 Pillow 的 Python 可运行图集像素验证；CI 使用 Node 24、Python 3.12 和 Pillow。版本目录与发布记录若产生新改动，要明确暂存、审阅并纳入最终发布提交，再对最终 HEAD 重新生成部署标记与发布包。标签所指版本提交须为最终 main 的祖先，不能沿用其他未集成分支的标签来声称已发布。

新增运行文件同步 `scripts/build-site.cjs` 清单；默认门禁只验证三国现行引擎；历史测试按需从 GitHub 获取，单独记录。设备测试、实际全剧情通关和外部分享文件核验有各自边界，不由 HTTP 冒烟替代。

## 3. 标签与推送

| 项目 | 标签 |
|---|---|
| 首页 | `site/home/vX.Y.Z` |
| 坦克大战 | `game/tank-battle/vX.Y.Z` |
| 三国 | `game/three-kingdoms/vX.Y.Z` |
| 超级玛丽 | `game/super-mario/vX.Y.Z` |
| 墨水屏小站 | `game/idle-screen/vX.Y.Z` |
| Mac 软件资源库 | `resource/mac-software-library/vX.Y.Z` |
| 粉丝资源 | `content/fan-resources/vX.Y.Z` |

业务稳定版本先推本次标签，再推包含对应版本与最终验证结果的 main。不要创建旧式全局标签，不强推 main 或覆盖已公开版本标签。只有管理文档变化时不抬升七个业务版本。

## 4. 部署与线上验收

Pages 工作流只允许 main：完整检出历史/标签 → 生成版本目录 → 全仓测试 → 写部署提交标记 → 生成并验证 `.site/` → Pages 部署 → 线上验收。

```bash
node 创意空间首页/测试/published_site_test.mjs \
  "https://sunsharebay-lgtm.github.io/TK/" \
  "<本次最终部署提交完整 SHA>"
```

验收跟随根页与三国等 HTML 跳转，核对七项目入口、实际脚本、核心数据、非空创意目录、Mac 软件 JSON、粉丝资源和详情页。CDN 旧提交必须等待或调查，不能只看 HTTP 200。

发布完成必须具备：远端提交/标签正确，目标提交对应 Actions 成功，部署标记匹配，线上验收通过。将提交、标签、Actions、验收结果和剩余边界记录回台账与项目交付记录。

## 5. 失败处理

- main 更新但线上旧：核查对应 Actions、Pages 环境与部署标记。
- 标签意外触发部署或被保护环境拒绝：检查工作流，保持 main 唯一部署来源。
- 推送非快进：获取最新 main，保留本次修改后重新集成、验证，不强推。
- 门禁失败：区分本次回归和已有问题，修复/验证后继续；不得忽略失败宣称完成。
- 发布结束后仍有本地差异：逐项标明本地记录、素材或未发布业务改动，不把它们混入下次需求。
